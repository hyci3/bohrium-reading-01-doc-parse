## 1. 项目背景

科研论文 PDF 常包含双栏或多栏排版、跨栏图表、复杂表格、数学公式、特殊字符、脚注、参考文献以及扫描页面。直接使用通用文本提取工具，容易出现漏行、串栏、段落误合并、表格结构丢失、公式符号失真和证据位置无法追溯等问题，进而影响后续翻译、问答、信息提取与知识结构化。

本项目需要构建一个可由 Agent 调用的 Skill。平台将在三个固定科研案例上，分别运行不加载该 Skill 的基础 Agent 与加载该 Skill 的 Agent，并比较实际结果。项目不得以预制答案替代真实解析，应通过可复核的运行产物证明解析质量、效率、可靠性和可复用性。

## 2. 建设目标

### 2.1 总体目标

构建一套证据导向、结构清晰、异常可说明、结果可复核的科研文献 PDF 解析工作流，使 Agent 能够基于真实论文完成题目指定的解析、翻译、问答、提取、核验或知识结构化任务。

### 2.2 具体目标

1. **提得全**：尽可能完整提取正文、标题、作者与单位、摘要、章节、图表题注、脚注和参考文献，避免将页眉页脚误并入正文。
2. **排得对**：还原文档阅读顺序，减少双栏、多栏、跨栏及跨页内容中的串栏、错行和段落错误拼接。
3. **拆得清**：识别章节层级、段落边界、表格结构、公式编号、上下标、希腊字母和特殊符号，形成可继续处理的数据。
4. **核得回**：为结构块和关键任务结论保留页码、段落、字段、图表、公式或区块位置等来源信息。
5. **做得实**：根据案例任务生成实际答案或结构化结果，而非仅返回看似完整的全文文本。
6. **说得清**：明确区分成功、部分完成、无法判断和拒答，披露材料缺失、识别失败、证据冲突及处理限制。
7. **可复用**：提供完整加载、调用、配置、依赖、示例和自查说明，不依赖作者个人文件或未说明的手工操作。
8. **省上下文**：面向名义总上下文约 256K tokens 的模型，以磁盘结构化产物、紧凑索引、按需证据选择和分段写入减少全量文本、原始坐标、页图及日志对模型上下文的占用。

### 2.3 建设原则

- 以真实输入文件和原论文为事实依据，不依据文件名或可能错误的领域标签推断论文内容。
- 解析结果与任务答案均不得编造；未报告、不可辨认和证据不足不得写成确定事实。
- 优先保证正确性、完整性、证据可追溯性和运行稳定性，再增加增强功能。
- 优先采用可重复执行的规则和脚本处理确定性工作，模型用于需要语义判断的环节。
- 不要求建设覆盖所有版式的完整 PDF 解析系统，但基础链路必须通用，所选突破方向必须形成实质改进。

## 3. 项目范围

### 3.1 范围内

1. Skill 的触发、加载、调用和执行流程。
2. 案例任务说明、输入约束、原始输出契约和 PDF 文件的识别与校验。
3. 文字版、扫描版及混合页面 PDF 的类型检测和处理路径选择。
4. 正文提取、版面分析、阅读顺序整理和基础章节结构识别。
5. 图表题注、表格、公式、特殊字符、脚注和参考文献的识别或保真处理。
6. 按案例要求完成解析、翻译、问答、提取、核验或知识结构化。
7. 页码与区块级证据定位、不确定性标注、冲突说明和运行状态记录。
8. 结构化结果保存、部分结果提前保存、运行自查和异常处置。
9. Skill 使用说明、方法说明、依赖说明、最小调用示例及复用资源。
10. 至少一个明确突破方向的增强实现，例如多栏阅读顺序、复杂表格、章节结构、公式与特殊字符或扫描件 OCR。
11. 使用自建或获授权样例形成可复核的质量、效率和创新证据，说明相对基础处理路径的改进及适用边界。
12. 在资源预算允许时沉淀可分享的版式样本、样例题集、Benchmark 方法和实践经验，但不替代平台正式案例与对照。
13. 面向约 256K tokens 名义上下文的分层阅读、上下文选择、预算估算、分段产物合并和超预算降级。

### 3.2 范围外

1. 提交三个正式案例的预制答案、白板或伪造的正式测试结果。
2. 在缺少真实输入时猜测论文内容、实验数据或任务答案。
3. 对图表和公式进行题目未要求的科学含义解释。
4. 承诺支持所有 PDF 版式、所有语言或所有损坏文件。
5. 自行编造平台测评分数、运行轨迹、工具状态或基准对比结果。
6. 依赖未声明的个人路径、私有服务、人工复制粘贴或其他不可复现操作。

### 3.3 待确认范围

- 主要创新突破方向及其优先级。
- `environment/resources.yaml` 中各工具的准确调用方式、版本和限制。
- `interface-example` 中的输入示例和标准调用接口。
- 各正式案例的原始 `output_contract` 字段及具体科研任务。
- 三个正式案例的版式、语言、页数、是否扫描件及表格和公式复杂度。

| 复用与维护人员 | 在其他科研 PDF 上部署、修改和扩展 Skill | 依赖清楚、脚本可运行、边界和失败方式明确 |

## 5. 输入要求

### 5.1 正式运行输入

| 输入 | 预期位置或来源 | 要求 |
|---|---|---|
| 案例数据 | `/input/case.json` | 读取案例标识、任务信息、材料路径和原始输出契约，不预设字段内容 |
| 案例任务说明 | 正式运行提供的 `task.md` | 识别任务类型、输入约束、交付要求和证据范围 |
| 原始科研 PDF | 案例材料指定的实际路径 | 直接处理真实 PDF，不依赖预先提取的答案层 |
| 环境与工具说明 | `environment/resources.yaml` | 作为资源入口；捆绑文件按该文件所在目录的相对路径解析，声明的预安装运行路径对应平台固定镜像 |
| 官方执行环境 | official DeepSeek Harness | 平台安装实际 Skill 后，通过该 Harness 在每个固定原始案例上运行；项目不得假定或替换正式评测执行器 |
| 其他案例材料 | 案例明确提供的附件或配置 | 仅处理任务授权范围内的材料，并记录来源 |

### 5.2 输入识别与校验

1. 必须读取实际文件，不得仅根据材料名称、标签或文件扩展名推断其内容。
2. 必须提取并保留 `case_id`；若输入缺失或无法解析，应记录具体原因。
3. 必须识别原始 `output_contract` 的全部字段，后续输出不得擅自删除、改名或增加与之冲突的定义。
4. 必须检查 PDF 是否存在、可读取、是否加密、页数是否可获取、是否具有文字层以及是否可能为扫描件。
5. 材料缺失、任务要求无法判断、文件无法读取和解析失败必须分别记录，不得合并为笼统的错误状态。
6. 任务说明、实际文件和元数据存在冲突时，应说明冲突；科学事实以原论文和任务明确指定的事实依据为准。

## 6. 总体工作流程

Skill 应引导或执行以下流程：

1. **读取契约**：解析案例标识、任务类型、输入材料、输出字段和限制。
2. **检查输入**：验证文件存在性、可读性、PDF 状态和工具可用性。
3. **建立 early result**：在主结果完成前，先保存包含输入标识、当前状态和已知限制的诚实结果，避免中断后无任何产物。
4. **解析文档**：根据文字层和页面情况选择文本提取、版面分析或 OCR 路径。
5. **恢复结构**：整理阅读顺序、章节、段落、表格、公式、题注、脚注和参考文献，并保留来源位置。
6. **选择上下文**：先形成紧凑文档索引，再按任务选择必要章节和证据区块；全文、原始坐标、页图和日志默认仅保存到磁盘，不整体注入模型。
7. **执行任务**：基于所选的充分证据完成题目要求的问答、翻译、提取、核验或知识结构化；全文献任务采用分段产物与确定性合并。
8. **绑定证据**：将关键结论与原文页码和相关区块关联，标明未报告或不确定项。
9. **质量自查**：检查输出字段、文字完整性、阅读顺序、结构、证据、上下文预算和异常说明。
10. **保存交付结果**：向 `/app/output` 写入最终 `result.json` 及任务要求的其他可编辑产物和预览。
11. **记录变更**：保留实际处理步骤、状态变化和重要修复记录，不记录虚构操作。

## 8. 证据与可追溯性要求

### 8.1 证据粒度

1. 文档结构块至少保留 PDF 物理页码；可获得时同时保留页面边界框、区块编号或其他坐标定位。
2. 章节、段落、表格、图题和公式应具有稳定标识，便于结果字段引用。
3. 表格结果应能定位到原表页码；跨页表应记录全部相关页。
4. 公式结果应能定位到公式编号；无编号时使用页码和区块位置。
5. 问答、翻译、提取与知识结构化中的关键内容应引用相应证据，不得只给结论而无来源。
6. 论文印刷页码与 PDF 物理页码不一致时，应说明所采用的页码体系，必要时同时记录两者。

### 8.2 不确定性与冲突

- **未报告**：任务所需信息在已检索材料范围内没有明确记载。
- **无法判断**：存在相关材料，但因文字、图像、结构或证据不足而不能可靠判断。
- **识别失败**：工具或处理流程未能读取相应内容，记录失败环节和原因。
- **材料冲突**：不同位置、字段或材料之间存在不能同时成立的内容，应列出各自来源。
- **推测内容**：原则上不进入事实性主结果；任务确需推断时，应与原文事实清楚区分并给出依据。

### 8.3 质量自查与门控

1. **契约完整性检查**：逐项核对原始 `output_contract` 字段、`case_id` 和必需产物；检查 JSON 语法、字段类型及占位符残留。未通过时不得声明完整成功。
2. **页面覆盖检查**：记录 PDF 总页数、已处理页、跳过页和失败页；对“未报告”的判断应说明已检查的材料范围，不能以局部检索代替全文检查却声称全文未报告。
3. **阅读顺序抽查**：对标题页、双栏起始页、跨栏图表页和跨页段落等高风险页面，将提取结果与页面渲染图或原始布局进行对照，重点检查串栏、重复页眉页脚、题注混入和错误续接。
4. **结构与符号检查**：对任务涉及的表格和公式进行针对性抽查，核对行列归属、表头层级、公式编号、上下标及希腊字母；不能确认时降低相应结果的状态或置信说明。
5. **证据引用完整性检查**：确认引用页码属于当前 PDF，区块或结构标识确实存在，引文与原文一致，且证据能够支撑对应结论而非仅与主题相关。
6. **状态一致性检查**：主结果、限制字段和运行状态应相互一致；仍存在影响任务答案的未解决项时，不得输出无保留的“成功”。
7. **修复再验证**：对自查发现的问题进行修复后，只重新验证受影响内容及必要的全局契约，记录实际变更，避免无目的全文重跑消耗预算。

## 9. 输出要求

### 9.1 输出位置与文件

1. 中间工作文件放入 `/app/work`。
2. 最终结果及可编辑交付物放入 `/app/output`。
3. 必须生成 `/app/output/result.json`，包含原始 `output_contract` 的全部字段和 `case_id`。
4. 若任务生成可编辑 Office、幻灯片或图示文件，应同时生成真实的 PDF 或 PNG 预览供检查。
5. 输出文件应反映本次实际运行，不得从 Skill 资源中复制预制正式答案。

### 9.2 结果语义字段

下表定义必须覆盖的信息语义，实际字段名和嵌套方式以案例原始 `output_contract` 为准：

| 信息 | 内容要求 |
|---|---|
| 案例标识 | 保留输入的 `case_id`，不得编造或混用 |
| 主结果 | 按任务给出答案、翻译、结构化字段、表格或知识结构 |
| 证据与来源 | 页码、段落、字段、图表、公式或区块位置，以及必要的原文摘录 |
| 运行状态 | 明确采用成功、部分完成、无法判断或拒答等状态，并记录原因 |
| 不确定性 | 标明低置信度识别、材料缺口、结构歧义和未解决冲突 |
| 限制与人工接管 | 指明未覆盖范围、失败页面或区块，以及后续人工检查位置 |
| 变更记录 | 记录实际执行的重要处理、修复和状态变化 |

### 9.3 状态判定

- **成功**：任务要求均已完成，必要证据和规定产物齐全，不存在影响主结果的未披露问题。
- **部分完成**：已形成部分可用结果，但仍有页面、字段、结构或子任务未完成；必须列出具体边界。
- **无法判断**：输入可部分理解，但证据不足以形成题目要求的可靠结论。
- **拒答**：因明确限制或无法处理的输入而不能执行；必须给出具体原因，不得用作一般解析失败的笼统替代。
- **运行失败原因**：实际发生运行失败时，必须在规定的状态、原因或错误字段中明确记录，并与材料缺失和无法判断分开说明；具体状态取值以原始 `output_contract` 为准，不擅自增加冲突枚举。

## 10. 异常处理要求

| 异常场景 | 处理要求 |
|---|---|
| 输入文件缺失 | 指明缺失文件和所需位置，输出可区分的失败状态，不继续虚构解析结果 |
| `case.json` 或任务约束无法解析 | 保留错误详情和已识别信息，说明哪些输出契约字段无法确定 |
| PDF 加密或不可读取 | 记录工具返回的实际原因；不能将加密文件当作空白扫描件 |
| 无文字层扫描件 | 切换至 OCR 路径；OCR 不可用时给出页面范围和人工接管建议 |
| 图片型表格 | 不得因无单元格文字层而判定表格为空；应尝试可用的图像或 OCR 路径，并区分文字识别错误与表格结构错误 |
| OCR 质量低或局部乱码 | 标注低置信度区域，保留可核对的页码或图像位置，不按上下文猜成确定文字 |
| 字体乱码或特殊字符失真 | 尝试可用的替代提取方式；仍不能恢复时保留原始表示并披露问题 |
| 多栏顺序无法可靠确定 | 输出可确认部分，同时标记可疑页面和区块，不静默拼接 |
| 表格结构无法可靠恢复 | 保留表格原始文字和位置，明确仅结构不确定，不伪造合并关系 |
| 页码错乱或印刷页码不一致 | 使用明确的页码体系记录位置，并披露差异 |
| 原文信息未报告或相互冲突 | 分别标记未报告或冲突，列出相关证据，不自行补数 |
| 工具不可用或超时 | 保存已有部分结果，记录失败工具、执行阶段和可恢复位置 |
| 预算不足 | 优先完成主结果、证据、状态和必需文件；不为扩展功能牺牲基本交付 |
| 模型上下文预算耗尽 | 保存紧凑索引、已选证据、全文献分段和续接游标，明确未覆盖范围；不得通过无痕截断或无依据摘要冒充完整结果 |

## 11. 非功能需求

### 11.1 运行预算与效率

1. 正式执行须遵守 64 次模型请求、900 秒及单次响应 16384 tokens（含推理）的题面预算。
2. OCR、模型和工具调用应有明确用途，避免重复全文传输、无差别 OCR 和无效重跑。
3. 应尽早保存部分交付物，再逐步提升结果完整性和质量。
4. 效率提升不得通过省略证据、跳过异常检查或复制预制答案实现。
5. 模型、来源与案例版本、运行时、预算和实际原生轨迹以平台记录为准；项目不得另造或修改这些正式记录。
6. 实际服务失败按平台规则单独暂停处理，不得将其伪造成正常完成、论文解析失败或本地性能数据。

### 11.2 稳定性与可重复性

1. 相同输入和配置下重复运行应产生语义一致的结果和有效产物。
2. 临时文件和输出文件路径应清晰，不得覆盖其他案例结果。
3. 解析规则、脚本和模型处理环节的失败不得导致已有诚实结果丢失。
4. 对不同页数、语言和声明支持的版式，应按能力边界正常工作或明确降级。
5. 正式评测包含三个案例、每个条件三次重复；实现不得依赖前次运行遗留状态、固定案例顺序或人工续接才能完成。

### 11.3 可移植性与依赖

1. 不得依赖作者个人绝对路径、未声明软件、私有凭据或手工操作。
2. 所有依赖须说明版本、安装方式、路径、来源和使用条件。
3. 优先使用运行环境固定提供的 PDF 文本提取、页面渲染、OCR 和科学计算工具。
4. 脚本与资源路径须与实际提交版本一致；使用 `environment/resources.yaml` 时，捆绑资源按该目录的相对路径定位，预安装路径以固定镜像声明为准。
5. Skill 内资源引用应基于安装位置或可靠的相对路径解析，不得依赖调用方当前工作目录恰好为某一位置。

### 11.4 Skill 资源约束

1. Skill 安装后由平台置于 `/skills/weekly-skill`，不得假定其他安装位置。
2. 提交时必须在 `/app/submission/` 下创建 `SKILL.md`，并配置合法的 `name`、`description` YAML frontmatter。
3. Skill 资源最多 50 个 UTF-8 文本文件。
4. 单个资源文件不超过 500 KB，总大小不超过 2 MB。
5. 不使用符号链接。
6. 正式运行时产生的二进制文件可独立保留，但不能用其替代规定的有效 JSON 结果。

### 11.5 易用性与可维护性

1. 说明文件应包含用途、适用条件、调用方式、输入输出、依赖、配置、限制、失败处理和自查方法。
2. 示例应简洁完整，且明确标注为示意数据和示意输出。
3. 代码、配置和方法说明应保持一致，避免说明中声称存在未实际实现的能力。
4. 关键规则和处理参数应便于检查和修改。

### 11.6 约 256K tokens 模型上下文优化

#### 11.6.1 预算口径

1. 上下文预算以 tokens 计，不以字符数、文件大小或 PDF 页数替代。名义默认值为 256,000，实际配置应取模型声明上限、Harness 限制和用户配置中的最严格可用值。
2. 上下文占用至少包括系统提示、Skill 指令、用户任务、工具结果、历史模型响应和重新注入的证据，不能只计算当前送出的原文。预算状态应支持 Agent 在主要请求后登记实际 tokens 或保守估算的非原文交互占用；无法取得实际值时应降低原文注入上限，不能把固定预留视为不被突破的保证。
3. 默认初始参数如下，均为保守开发起点而非实测最优值；调整后必须保留配置和实际测试记录：

| 参数 | 初始值 | 用途 |
|---|---:|---|
| `context_budget_tokens` | 256,000 | 名义总上下文上限，可按实际模型下调 |
| `runtime_reserve_tokens` | 65,536 | 全案系统提示、Skill、工具调用、状态与非原文交互的预留 |
| `case_source_injection_budget_tokens` | 96,000 | 全案累计注入论文原文、索引和证据摘录的软上限，不表示每篇都应使用尽 |
| `single_selection_max_tokens` | 24,000 | 单次按需证据选择的最大原文规模，留出当前响应和指令空间 |
| `response_reserve_tokens` | 16,384 | 单次模型生成及推理的最低预留，遵守题面单次响应限制 |
| `document_index_max_tokens` | 12,000 | 文档紧凑索引上限，包含在累计原文注入预算中 |
| `single_tool_report_max_tokens` | 2,000 | 单次状态、校验或错误报告的推荐上限，详细日志保留在文件 |

4. 单次选择不得仅按 `single_selection_max_tokens` 截字，还应遵守块、段落或表格等语义边界，并向前保留标题路径和证据引用。
5. 256K 优化不等于允许每轮发送 256K；默认宁可进行小批量选择、读取磁盘结构和针对性核验，也不进行全文多轮复述。

#### 11.6.2 分层读取

1. 第一层只读案例契约、任务、处理状态和紧凑索引；第二层按任务读取相关章节、题注、表格或公式；第三层只读取回答关键问题所需的原文块和必要的渲染页。
2. `document.json`、原始坐标文件、完整 OCR 结果和页图集合属于磁盘证据层，不得作为常规整体上下文输入。
3. 选择结果应按原阅读顺序输出，包含 `block_id`、物理页码和章节路径；截断必须给出下一批游标或被省略范围，不能无痕中断句子和数值。
4. 同一证据需要复用时优先引用已有 `block_id` 和本地文件游标，避免在多次模型请求中重复发送长引文。
5. 不依赖外部向量数据库、嵌入服务或子 Agent 才能工作；无可用语义检索时使用确定性关键词、章节和字段过滤。

#### 11.6.3 全文献任务与超预算处理

1. 对全文翻译、全文提取或全结构化任务，按章节或连续页段处理，每段独立写入产物并记录术语表、输入哈希、覆盖范围和状态。
2. 后续分段只携带必要的任务约束、当前段和紧凑术语表，不重复注入此前全部原文、译文和思考过程；最终拼接由确定性程序完成，Agent 负责必要校验。
3. 如果当前 Agent 无法释放历史上下文且累计预算将耗尽，不得假设可以无限新开会话或调用子 Agent。应保存已完成分段、待处理游标和缺失范围，输出部分完成及人工续接点。
4. 页图 tokens 或模型图像费用未知时，按独立保守预算和最少必要页数处理；不得把图片视为不占上下文。
5. tokenizer 不可用时，允许字符与混合语言的保守估算，但必须标记 `token_count_method=estimated`、安全系数和误差未知，不能输出伪精确 tokens。

### 14.1 评分驱动的优先级约束

1. **先保实际效果**：实际效果与使用增益合计 65 分，任何文档、展示或扩展功能不得挤占主结果、正确性、证据和稳定性所需预算。
2. **增益必须相对可证**：不得只声称“更快”或“更准”；应说明比较对象、相同条件、评价指标和实际记录，正式对照由平台生成。
3. **创新必须有边界**：明确新增能力相对于基础 Agent 或现有处理路径解决了什么问题，同时披露失败条件和不可用场景。
4. **效率记录不得混用**：平台原生轨迹、正式案例结果和自有样例测量应分别标识，不能互相替代。
5. **内部目标不是得分承诺**：本规格只建立需求与评分点的追踪关系，不预设或推算最终成绩。

## 15. 建议实施顺序

1. **第一阶段：契约与最小闭环**  
   完成输入识别、PDF 状态检查、基础文本解析、证据模型、异常状态和 `result.json` 输出，确保任何中断均有诚实产物。
2. **第二阶段：核心质量提升**  
   优先解决阅读顺序、章节层级、题注、页眉页脚及跨页衔接，建立页面与区块级定位。
3. **第三阶段：突破方向实现**  
   结合真实工具条件和可自建样例，选择复杂表格、公式保真、扫描件 OCR 或其他明确方向进行深入增强。
4. **第四阶段：可靠性与复用验证**  
   完成异常测试、重复运行检查、预算检查、最小示例、使用说明和交付一致性检查。
